## P1-4 本地 CLI 输出 UTF-8 截断

- **结论：确认。** `execute_local_cli_turn` 的 stdout/stderr 读线程对每个
  read 块直接 `String::from_utf8_lossy`，中文（3 字节）跨块即变 U+FFFD。
  API 的 SSE 路径按行字节处理，确实没有这个问题，未动。
- **修复（17f2b46）：** 读线程发送原始 `Vec<u8>`，接收端用新增的
  `Utf8ChunkDecoder`（`std::str::from_utf8` + `valid_up_to`）增量解码，
  尾部不完整字节留给下一块；真正无效的字节才按单个 U+FFFD 输出；
  循环结束时 `finish()` 收尾。
- **测试：** `utf8_chunk_decoder_reassembles_split_multibyte_chars`
  （「你好，世界」15 字节，在全部 16 个切分点拆成两块重组后等于原文）、
  `utf8_chunk_decoder_handles_byte_by_byte_and_mixed_ascii`（逐字节喂入）。
- **行为变化：** CLI 输出中的中文不再出现半字乱码；其余行为不变。

## P1-5(a) 子进程退出后仍等到 120 秒超时

- **结论：确认（逻辑层面）。** 接收循环只在所有 sender 被 drop
  （`Ok(None)`）时退出，`Finished` 只记录退出码。带 MCP server 等
  衍生进程继承 stdout 管道时，管道不关闭，循环等到 deadline 才返回
  「超时」，丢弃已有正常输出。
- **修复：** 收到 `Finished` 后只给读线程约 500ms 排空（`drain_deadline`），
  到时即用已有输出返回；不再等管道关闭。
- **测试：** `cli_turn_returns_after_process_exit_despite_inherited_pipe`
  （`sh -c 'echo HELLO-DRAIN; sleep 5 &'`：主进程退出、孙进程占着管道，
  须在 10 秒内返回 `HELLO-DRAIN`；旧实现需 120 秒才超时返回）。
- **行为变化：** CLI 退出后最长再等 500ms 即返回；此前会等到总超时。

## P1-5(b) 超时只杀直接子进程

- **结论：确认。** watcher 线程只 `child.kill()`，包装脚本（`sh -c` /
  `.cmd` / `npx`）的孙进程会残留。
- **修复：** Unix：`Command::process_group(0)` 让子进程自成进程组，
  超时/取消时 `killpg(pgid, SIGKILL)`，失败再回退 `child.kill()`。
  Windows：子进程创建后挂入 Job Object（`windows` crate，
  `CreateJobObjectW` / `AssignProcessToJobObject`），超时/取消时
  `TerminateJobObject`，挂入失败则回退 `taskkill /T /F`。
- **测试：** （待补：Unix 进程组杀灭的集成测试）
- **手工验证（Linux）：** （待补步骤）
- **行为变化：** 超时或手动停止后，孙进程不再残留。

## P1-5(c) 120 秒总超时太短

- **结论：确认。** `deadline` 写死 120 秒；且超时返回时丢弃已收集输出。
  另确认：前端**没有**面向外部成员（API/CLI）的「停止」按钮——
  `main.ts` 群聊界面只有同步/沉淀按钮，`session_manager.rs` /
  `site_adapters.rs` 里的「停止」选择器针对的是 Muse/Hark 网页自身的
  停止按钮，与 CLI 子进程无关。
- **修复：**
  - `ExternalAgentRecord` 新增 `timeoutSecs`（默认 600 秒）与
    `idleTimeoutSecs`（默认 60 秒，无输出才判超时），旧配置缺失时
    按默认值补齐；`normalize_external_agent_input` 做范围校验
    （总超时 30–3600 秒，空闲超时 10–600 秒，越界拒绝；迁移解析
    越界值按默认处理）。
  - 外部成员表单新增两项超时输入（CLI 与 API 成员共用总超时）。
  - 超时错误附带已收集的部分输出（前 500 字）。
  - 取消令牌：`SessionManager` 内登记 `(group_id, msg_id) -> AtomicBool`，
    新增 Tauri 命令 `cancel_external_member_turn`（另补
    `src-tauri/permissions/autogenerated/cancel_external_member_turn.toml`、
    `build.rs` 的 `APP_COMMANDS` 与 `capabilities/manager.json` 授权，
    否则构建脚本报 `Permission allow-cancel-external-member-turn not found`）；
    群聊界面对 streaming/sending 状态的外部成员消息显示「停止」按钮；
    取消后 CLI 走进程组杀灭，API 丢弃响应流，已有部分输出保留。
- **测试：** `normalize_external_agent_validates_timeouts`；
  `cli_turn_total_timeout_keeps_partial_output`（2 秒总超时，错误含
  `PARTIAL-OUTPUT`）；`cli_turn_idle_timeout_fires_without_output`
  （输出一行后 2 秒无输出即判空闲超时）；`cli_turn_cancel_flag_kills_tree_and_returns_partial`
  （500ms 后置位令牌，返回 `BEFORE-STOP`）。
- **已知局限：** API 侧取消在 P1-6 后改为 `tokio::select!` + 200ms
  节拍轮询，最多 200ms 内注意到（流停滞超过 60 秒则由 read_timeout
  触发断流，按截断返回已有文本）。
- **行为变化：** 默认总超时由 120 秒改为 600 秒；新增 60 秒空闲超时；
  超时不再丢弃已收集输出；新增手动停止能力。

## P1-5(d) Windows 找不到 .cmd 垫片

- **结论：待在 Windows 实测。** 代码审查确认两点属实：`Command::new("codex")`
  在 Windows 上只自动补 `.exe`，npm 全局安装的 `.cmd` 垫片确实找不到；
  Rust ≥ 1.77 对含 `"` / `%` 的批处理参数会拒绝启动。
- **修复（仅 Windows 代码，Linux 上编译不到）：**
  - 新增 `resolve_cli_executable`：先试裸名，再遍历 `PATH × PATHEXT`
    （默认 `.COM;.EXE;.BAT;.CMD`），带路径时也按 PATHEXT 补全；
    返回完整路径与是否为批处理垫片，找不到时报中文错。
  - 对 `.cmd` / `.bat`：prompt 一律走 stdin（无 `{prompt}` 时本就
    走 stdin，不用改）；`{prompt}` 与批处理垫片同时出现时，
    `check_batch_prompt_conflict` 返回明确中文错误，提示去掉
    `{prompt}` 改用 stdin。
- **测试：** `batch_prompt_conflict_requires_stdin`（全平台可跑）；
  `resolve_cli_executable_finds_cmd_shim`（仅 Windows 编译/运行，
  Linux 上跳过）。
- **手工验证（Windows，待实测）：**
  1. `npm i -g @openai/codex`（或任意带 `.cmd` 垫片的 CLI），确认
     `%APPDATA%\npm\codex.cmd` 存在、`codex` 在 PATH 里。
  2. 群聊里新建本地 CLI 成员，命令填 `codex`，参数留空（走 stdin），
     发一句话：应正常出回复，不再报「找不到程序」。
  3. 同一成员参数改成 `exec {prompt}`：保存/发送时应看到中文错误，
     提示去掉 `{prompt}` 改用 stdin，而不是启动失败。
  4. 命令填一个不存在的名字（如 `maam-no-such-cli`）：应看到中文错
     「已按 PATH × PATHEXT 查找，请确认已安装并加入 PATH」。
  5. prompt 含 `"` 或 `%`（如 `说 "你好" 100%`），走 stdin 的成员应
     正常执行，不报批处理参数错误。
- **行为变化：** Windows 上 `codex` 等 npm 全局 CLI 能被找到；
  批处理垫片 + `{prompt}` 占位符时由启动失败改为明确中文报错。

## P1-5(e) macOS 的 PATH 补全不完整

- **结论：确认。** `build_augmented_path` 只补 homebrew、`~/.local/bin`、
  `~/.npm-global/bin`、`~/.cargo/bin`，没有 nvm / volta / bun / pnpm /
  `~/.claude/local`。
- **修复（仅 macOS 代码，Linux 上编译不到）：** 启动 CLI 前用
  `$SHELL -ilc 'printf %s "$PATH"'`（3 秒超时）读取登录 shell 的 PATH
  并用 `OnceLock` 缓存；失败（超时/非零退出/空输出）回退到现有
  硬编码列表，硬编码列表另补 `~/.volta/bin`、`~/.bun/bin`、
  `~/Library/pnpm`、`~/.claude/local/bin`。合并顺序：登录 shell 的
  PATH 在最前，再接当前进程 PATH，最后补硬编码目录，全程去重
  （`merge_augmented_path`，全平台可单测）。nvm 的版本目录是通配符
  路径（`~/.nvm/versions/node/*/bin`）不硬编码，靠登录 shell 的 PATH
  覆盖。注意：首次读取最多阻塞 3 秒（之后走缓存），发生在 CLI 启动前。
- **测试：** `merge_augmented_path_prefers_login_shell_and_dedups`、
  `merge_augmented_path_without_shell_path_keeps_old_behavior`
  （全平台可跑）；登录 shell 读取本身仅 macOS，见手工步骤。
- **手工验证（macOS，待实测）：**
  1. 在 `~/.zshrc`（或 `~/.bash_profile`）里确认有 nvm/volta/bun
     的 PATH 配置，如 `export PATH="$HOME/.nvm/versions/node/v22/bin:$PATH"`；
     `echo $SHELL` 应为 `/bin/zsh`（或 bash）。
  2. 从 Finder 启动本应用（不要从终端启动——终端启动自带 shell PATH，
     测不出区别），群聊里新建本地 CLI 成员，命令填 `node` 或 `bun`，
     发一句话：应正常执行，不再报「找不到程序」。
  3. 对照：把 `~/.zshrc` 里的 PATH 配置临时注释掉，从 Finder 重启
     应用，同一成员应报找不到（证明走的是登录 shell 的 PATH）。
  4. 把 `$SHELL` 改成一个不存在的路径再启动：应用应正常启动、CLI
     回退到硬编码列表，不卡住（3 秒超时内返回）。
- **行为变化：** Finder 启动的 GUI 应用也能找到 nvm/volta/bun 等
  安装的 CLI；读取失败时行为与原来一致。

## P1-6 OpenAI 兼容 API 的 120 秒总超时截断长流式回复

- **结论：确认。** `execute_openai_api_turn` 用
  `reqwest::Client::builder().timeout(120s)`，覆盖整个响应体。
- **修复：** 去掉整体 `.timeout`，改用 `.read_timeout(60s)` 做空闲超时；
  外层用 `tokio::time::timeout` 包裹整轮调用，时长取成员配置的
  `timeout_secs`（默认 600 秒）。实现方式：原函数体抽成
  `execute_openai_api_turn_inner`，流式累积文本同步写入共享的
  `Arc<Mutex<String>>`；超时或断流（`chunk()` 报错，含 read_timeout
  触发）时，若已有累积文本则返回累积文本并追加「（回复被截断）」，
  无任何文本时才返回错误。另顺手把取消检查改成 `tokio::select!` +
  200ms 节拍，流停滞时取消最多 200ms 内生效（此前只在收到块的
  间隙检查）。
- **测试：** `api_turn_slow_stream_returns_partial_with_truncation_note`
  （本地慢速 SSE 服务器：发一块 `FIRST-CHUNK` 后停顿，2 秒总超时后
  返回该块 + 「回复被截断」）；`api_turn_timeout_without_any_content_errors`
  （一点内容没收到就超时，应报错而非空回复）。
- **行为变化：** 长流式回复不再在 120 秒被切断；被截断时消息中
  明确标注，不再静默丢失后半部分；流中断时同样保留已有文本。

## 新发现

- **共享 target 目录会跨 worktree 污染构建产物。** 多个并行任务共用
  `$HOME/workspace/.cargo-target-maam`，且各 worktree 是同一 crate
  （同名同版本），构建脚本指纹可能碰撞：P0-1 的两个命令
  （`continue_with_empty_config`、`restore_config_from_backup`）的
  autogenerated 权限文件在本次 `cargo test` / `cargo clippy` 运行中
  两次出现在本 worktree 的 `src-tauri/permissions/autogenerated/`。
  本分支代码完全不引用这两个命令，已删除、未提交，并从 P1-6 提交
  里 amend 掉。建议各 worktree 用独立 `CARGO_TARGET_DIR`，或至少
  提交前检查 `git status` 有无陌生 autogenerated 文件。
- **新增 Tauri 命令必须补三处，否则构建脚本直接失败。**
  `cancel_external_member_turn` 只加了 `lib.rs` 与 `build.rs` 的
  `APP_COMMANDS` 时，构建脚本报
  `Permission allow-cancel-external-member-turn not found`。还需补
  `src-tauri/permissions/autogenerated/cancel_external_member_turn.toml`
  与 `capabilities/manager.json` 里的 `allow-...` 授权。
- **自己写错的钳制被测试当场抓住。** P1-5(c) 初版把超时写成
  `agent.timeout_secs.max(30)` / `.max(10)`，导致 2 秒测试超时变成
  30/10 秒（耗时正好 30.06s / 10.06s）；校验已保证范围，钳制是多余
  的，已去掉。教训：默认值/钳制不要和校验范围打架。
- **P1-5(a) 的修复前复现曾被共享 target 目录文件锁挡住**，200 秒
  超时时仍未拿到锁、未执行；失败机理由旧循环结构（只有管道关闭
  才退出）直接确认，修复后测试 0.58 秒通过。
- **API 取消在 P1-6 后不再有停滞盲区。** (c) 初版只在收到块的间隙
  检查取消，流停滞时要等 read_timeout；现改为 `tokio::select!` +
  200ms 节拍，最多 200ms 内注意到。
